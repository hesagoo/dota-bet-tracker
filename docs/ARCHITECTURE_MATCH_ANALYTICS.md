# Будущий раздел «Аналитика матчей» с ИИ — архитектура и план

Статус: **только проектирование**, в приложении этого модуля пока нет. Цель документа — чтобы текущий код не мешал будущему развитию.

## Нейтральность раздела
Раздел «Аналитика матчей» — это нейтральная статистика и вероятностные оценки по матчам Dota 2.
- Он **не даёт рекомендаций** делать или не делать ставки и не использует формулировок вроде «верная ставка», «советуем», «гарантированно».
- Любая оценка сопровождается уверенностью, полнотой данных и историей точности модели; модель может ошибаться.
- Личный журнал ставок и банк остаются отдельной частью программы и не влияют на расчёты аналитики.

## Принципы
1. **Сбор данных, хранение, признаки, модель и оценка — отдельные слои.** Модель можно заменить, не трогая сбор данных.
2. **Прогноз ≠ факт.** Всегда показываем вероятность, степень уверенности, полноту данных и накопленную точность прошлых прогнозов.
3. **Сначала измеримость, потом сложность.** Начинаем с простой модели-базы (рейтинг Elo + форма), сравниваем всё с ней.
4. **Отдельная база** `analytics.db` рядом с `bets.db`: данные ставок и аналитики не смешиваются, сбой одной не ломает другую. Связь — по необязательному полю «матч» в ставке.
5. Приложение работает без интернета: показывает последние сохранённые данные с пометкой «данные от …».

## Слои
```
[Источники] → [Коллекторы] → [Нормализованное хранилище] → [Признаки] → [Модель] → [Прогнозы] → [Оценка точности]
 OpenDota        по одному      analytics.db (SQLite)         features     интерфейс     сохраняются    Brier, log loss,
 STRATZ          на источник    сырые ответы + таблицы        .py          Predictor     навсегда       калибровка
 PandaScore...   (плагины)
```
- **Коллекторы** (`analytics/collectors/`): один класс на источник, общий интерфейс `fetch_upcoming()`, `fetch_matches(since)`, `fetch_team(id)`. Лимиты запросов, повторы, кэш, запись «сырого» ответа в таблицу `raw_responses` (чтобы можно было пересобрать данные без повторных запросов).
- **Нормализация**: все источники приводятся к единым таблицам (ниже); у каждой записи есть `source`, `fetched_at`.
- **Признаки** (`analytics/features.py`): чистые функции «данные на момент T → вектор признаков». Правило: **только данные, известные до начала матча** (иначе утечка будущего и фальшивая точность).
- **Модель** (`analytics/models/`): интерфейс `Predictor.predict(features) -> Prediction` с полями: вероятность победы A/B, ожидаемые убийства, ожидаемая длительность, `confidence`, `data_quality`, `model_version`, `explanation`.
- **Оценка**: после матча результат подтягивается коллектором и сопоставляется с прогнозом.

## Источники данных (проверьте актуальные условия, лимиты и цены перед использованием)
| Источник | Что даёт | Замечания |
|---|---|---|
| **OpenDota API** | профессиональные матчи, команды, игроки, герои, пики/баны, длительность, убийства | есть бесплатный лимит, ключ повышает лимиты |
| **STRATZ API** (GraphQL) | детальная статистика матчей, игроков, драфтов | нужен токен, есть лимиты |
| **PandaScore** | расписание и результаты турниров, команды, live | бесплатный тариф ограничен; условия использования проверить |
| **Steam Web API** | live-матчи лиг, результаты | нужен ключ Steam |
| **Liquipedia** | турниры, составы, расписание | строгие правила использования API, нужна атрибуция; вручную не парсить |
| Dotabuff / DatDota | удобные сайты | **публичного API нет, парсинг обычно запрещён условиями** — не использовать |

Данные и коэффициенты букмекеров в аналитику матчей не подключаются: раздел описывает только игровую статистику и оценку вероятностей по ней.

## Схема хранения (`docs/analytics_schema.sql`)
Сущности: `teams`, `players`, `team_rosters` (состав по датам), `tournaments`, `matches` (серия), `games` (карта), `picks_bans`, `player_game_stats`, `upcoming_matches`, `raw_responses`, а также `predictions` и `prediction_outcomes`.
Версия схемы хранится в `PRAGMA user_version`, как и в основной базе.

## Прогнозы и честная оценка
Для каждого прогноза сохраняются: время, версия модели, использованные признаки (снимок), выданные вероятности, уверенность, список недоступных данных.
После матча считаем:
- **Brier score** и **log loss** (чем меньше, тем лучше);
- **калибровку**: из матчей с прогнозом «60%» команда должна побеждать примерно в 60%;
- точность по турнирам, по уровню уверенности, по свежести данных;
- сравнение с базовой моделью (Elo) и с «подбрасыванием монеты».
Если модель не лучше базовой, интерфейс так и скажет.

## Уверенность и доступность данных
- `data_quality` 0–100%: сколько ключевых признаков доступно (состав известен? игр у команды за 90 дней достаточно? есть личные встречи? драфт известен?).
- `confidence`: зависит от качества данных, размера выборки и калибровки модели (низкая выборка — широкий интервал). При малом числе игр вместо числа показываем «недостаточно данных».
- В интерфейсе всегда рядом: «Прогноз, а не гарантия. Точность модели на N последних прогнозов: X%».

## Модели по этапам
1. **База:** Elo команд (с учётом свежести, силы турнира, смены состава) → вероятность победы.
2. **Табличная ML-модель** (логистическая регрессия, затем градиентный бустинг) на признаках: форма, личные встречи, средние убийства/длительность, сила составов, формат серии. Регрессия отдельно для убийств и длительности.
3. **Драфт:** модель по героям (после накопления данных). Пики и баны доступны только после драфта, поэтому прогноз «до драфта» и «после драфта» — разные.
4. **Языковая модель (LLM)** — как *объяснитель*: по готовым цифрам формирует текстовое описание и сценарии. Вероятности выдаёт статистическая модель, а не LLM.

## План внедрения
| Этап | Результат | Объём |
|---|---|---|
| A | Каркас: `analytics/`, `analytics.db`, миграции, интерфейс коллектора, один коллектор (OpenDota) | малый |
| B | Раздел «Аналитика матчей»: список предстоящих матчей, карточка команды (форма, личные встречи, средние показатели) | средний |
| C | Накопление истории (фоновая загрузка), пики/баны, статистика игроков | средний |
| D | Baseline Elo + сохранение прогнозов + оценка точности | средний |
| E | ML-модели, калибровка, экраны уверенности и точности | большой |
| F | LLM-объяснения (текстовый разбор готовых цифр), экспорт отчёта по матчу | средний |

Рекомендация: этапы A–D дают рабочий инструмент с честной статистикой; к ML (E) переходить, когда накоплено несколько сотен матчей.
